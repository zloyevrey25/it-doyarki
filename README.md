## 💡 О проекте

После сбора урожая времени мало: продукция портится, покупатели предлагают разные цены, транспорт ограничен, а стоимость доставки отличается.

**Спаси урожай** — это веб-сервис, который рассчитывает оптимальный план поставок скоропортящейся продукции с учетом:

- 🍓 запасов продукции;
- 🛒 спроса покупателей;
- 💰 закупочных цен;
- 🚚 доступности и грузоподъемности транспорта;
- ❄️ холодильного оборудования и прибавки к допустимому времени доставки;
- ⏱️ допустимого времени доставки;
- 🛣️ стоимости рейсов.

Пользователь меняет исходные условия и нажимает «Пересчитать». До успешного ответа прежние показатели помечаются устаревшими. Сравнение до/после относится к расчётам по всем найденным покупателям; альтернативы на третьем шаге — к одному расчёту по выбранным направлениям.

## 📐 Оптимизационная модель

В основе сервиса лежит задача **смешанного целочисленного линейного программирования (MILP)**. Как и в классической задаче линейного программирования (ЗЛП), здесь задаются переменные, линейная целевая функция и система линейных ограничений. Отличие — наличие бинарных переменных выбора маршрута.

### Переменные

Непрерывная переменная

$$
x_{pbvr} \ge 0
$$

показывает, сколько килограммов продукта $p$ доставить покупателю $b$ автомобилем $v$ по маршруту $r$. Бинарная переменная

$$
y_{vr} \in \{0,1\}
$$

равна 1, если автомобиль $v$ использует маршрут $r$, и 0 в противном случае.

В реализации этим обозначениям соответствуют `shipped` и `chosen`:

```python
model = pulp.LpProblem("itinerary_profit", pulp.LpMaximize)
chosen = pulp.LpVariable.dicts("itinerary", (vehicle_ids, itinerary_ids), cat="Binary")
shipment_keys = [(product, buyer, vehicle_id, item["id"]) for product in products for vehicle_id in vehicle_ids for item in candidates for buyer in item["stops"]]
shipped = pulp.LpVariable.dicts("shipment", shipment_keys, lowBound=0, cat="Continuous")
```

[Источник: `backend/optimizer.py`, строки 102–105](https://github.com/zloyevrey25/it-doyarki/blob/main/backend/optimizer.py#L102-L105)

### Целевая функция

Модель максимизирует прибыль — выручку за поставленную продукцию за вычетом фиксированной стоимости автомобилей и стоимости маршрутов:

$$
\max Profit =
\sum_{p,b,v,r} Price_{pb}x_{pbvr} -
\sum_{v,r} FixedCost_v y_{vr} -
\sum_{v,r} RouteCost_{vr} y_{vr}.
$$

В коде целевая функция задаётся напрямую:

```python
revenue_expr = pulp.lpSum(data["prices"][product][buyer] * shipped[(product, buyer, vehicle_id, itinerary_id)] for product, buyer, vehicle_id, itinerary_id in shipment_keys)
fixed_cost_expr = pulp.lpSum(vehicles[vehicle_id]["cost"] * chosen[vehicle_id][itinerary_id] for vehicle_id in vehicle_ids for itinerary_id in itinerary_ids)
route_cost_expr = pulp.lpSum((vehicles[vehicle_id]["route_base_cost"] + by_id[itinerary_id]["total_distance"] * vehicles[vehicle_id]["cost_per_km"]) * chosen[vehicle_id][itinerary_id] for vehicle_id in vehicle_ids for itinerary_id in itinerary_ids)
profit_expr = revenue_expr - fixed_cost_expr - route_cost_expr
model += profit_expr
```

[Источник: `backend/optimizer.py`, строки 107–111](https://github.com/zloyevrey25/it-doyarki/blob/main/backend/optimizer.py#L107-L111)

### Ограничения

Допустимый план должен одновременно выполнять пять основных условий:

- **запасы:** суммарная отгрузка продукта не превышает его остаток на складе;
- **спрос:** покупателю нельзя отправить больше, чем он заказал;
- **грузоподъёмность:** загрузка маршрута не превышает вместимость выбранного автомобиля;
- **доступность авто:** недоступному автомобилю нельзя назначить маршрут, а доступному назначается не более одного;
- **время доставки:** если товар не успевает доехать с учётом скорости и времени работы холодильника, его объём на этом маршруте принудительно равен нулю.

$$
\sum_{b,v,r} x_{pbvr} \le Stock_p
$$

$$
\sum_{v,r} x_{pbvr} \le Demand_{pb}
$$

$$
\sum_{p,b} x_{pbvr} \le Capacity_v y_{vr}
$$

$$
\sum_r y_{vr} \le Available_v
$$

$$
x_{pbvr}=0
\quad\text{если}\quad
\frac{Distance_{br}}{Speed_v}>MaxTime_p+Refrigeration_v.
$$

Реализация ограничений по запасам, спросу и доступности:

```python
for product in products:
    model += pulp.lpSum(shipped[key] for key in shipment_keys if key[0] == product) <= data["stock"][product]
    for buyer in buyers:
        model += pulp.lpSum(shipped[key] for key in shipment_keys if key[0] == product and key[1] == buyer) <= data["demand"][product][buyer]
for vehicle_id in vehicle_ids:
    model += pulp.lpSum(chosen[vehicle_id][itinerary_id] for itinerary_id in itinerary_ids) <= int(vehicles[vehicle_id]["available"])
```

[Источник: `backend/optimizer.py`, строки 113–118](https://github.com/zloyevrey25/it-doyarki/blob/main/backend/optimizer.py#L113-L118)

Ограничения по грузоподъёмности и времени доставки:

```python
route_variables = [shipped[key] for key in shipment_keys if key[2] == vehicle_id and key[3] == itinerary_id]
model += pulp.lpSum(route_variables) <= vehicles[vehicle_id]["capacity"] * chosen[vehicle_id][itinerary_id]
model += pulp.lpSum(route_variables) >= 0.0001 * chosen[vehicle_id][itinerary_id]
for index, buyer in enumerate(item["stops"]):
    model += pulp.lpSum(
        shipped[(product, buyer, vehicle_id, itinerary_id)]
        for product in products
    ) >= 0.0001 * chosen[vehicle_id][itinerary_id]
    arrival = item["cumulative_distances"][index] / vehicles[vehicle_id]["speed_kmh"]
    for product in products:
        if arrival > data["max_delivery_time"][product] + vehicles[vehicle_id].get("refrigeration_hours", 0) + TOLERANCE:
            model += shipped[(product, buyer, vehicle_id, itinerary_id)] == 0
```

[Источник: `backend/optimizer.py`, строки 121–132](https://github.com/zloyevrey25/it-doyarki/blob/main/backend/optimizer.py#L121-L132)

### Связь с симплекс-методом и CBC

Если убрать бинарные $y_{vr}$, останется обычная линейная модель, для которой применим симплекс-метод. В полной MILP-модели CBC использует **branch-and-cut**: перебирает ветви дискретных решений, добавляет отсечения и решает линейные релаксации, связанные с классической ЗЛП.

```python
solver = pulp.PULP_CBC_CMD(msg=False, options=["preprocess off"])
status = pulp.LpStatus[model.solve(solver)]
```

[Источник: `backend/optimizer.py`, строки 138–139](https://github.com/zloyevrey25/it-doyarki/blob/main/backend/optimizer.py#L138-L139)

## 📦 Что учитывает модель

Для каждого продукта задаются:

- остаток на складе;
- максимальное допустимое время доставки.

Для каждого покупателя:

- положение в радиусе до 700 км от введённого адреса фермы;
- спрос;
- закупочная цена по каждому виду продукции.

Для транспорта:

- грузоподъемность;
- доступность;
- фиксированная стоимость использования;
- условная скорость и стоимость километра;
- базовая стоимость одного рейса;
- прибавка к допустимому времени доставки для машин с холодильником.

### Допущения расчёта

Компании и спрос демонстрационные, точки выбираются из ограниченного локального каталога реальных городов. Для продолжения нужны 4–5 покупателей с расчётным расстоянием до 700 км; радиус автоматически не увеличивается.
Расстояния между точками вычисляются локально как расстояние по прямой × 1,18. Время прибытия основано на накопленном расстоянии и условной скорости конкретной машины 65–70 км/ч. OSRM только визуализирует точки рейса по порядку; его длины и время не используются в ограничениях оптимизатора.
Одна машина выбирает не более одного рейса: прямого или парного с двумя упорядоченными остановками. Вместимость ограничивается общей загрузкой рейса, а срок продукта проверяется в его остановке. Модель не учитывает пробки, обратный путь и последовательности из трёх и более точек. +8/+12 часов холодильника — условная прибавка к допустимому времени доставки. Остатки — неотгруженный объём, не доказанная физическая порча; оценка риска основана только на запасе времени.
«До фикс. затрат» направления = выручка минус затраты направления. Фиксированная стоимость использованной машины вычитается один раз в итоговой прибыли плана; произвольного распределения этой стоимости между направлениями нет.

## 🔄 Сценарий для защиты

Мы специально реализовали сценарий из постановки кейса.

1. Загружается исходный набор данных.
2. Система рассчитывает оптимальный план.
3. Пользователь видит прибыль, расходы, остатки и поставки.
4. Одна машина переводится в состояние `unavailable`.
5. Одному покупателю повышается цена на клубнику.
6. Выполняется повторный расчет.
7. Система показывает новый план.
8. Можно сравнить результат **до / после** и убедиться, что все ограничения соблюдены.

Таким образом можно показать, что решение не захардкожено, а действительно пересчитывается оптимизатором.

## 🧩 Допущения

Проект создан как hackathon-MVP и использует демонстрационные данные.

В модели приняты следующие упрощения:

- один расчет рассматривается как один расчетный цикл;
- автомобиль имеет ограниченную общую грузоподъемность;
- одна машина выполняет не более одного прямого или парного рейса;
- парный рейс содержит две упорядоченные остановки, а время считается по накопленному расстоянию;
- стоимость рейса и фиксированная стоимость машины учитываются по одному разу на itinerary;
- дороги OSRM отображаются только на карте; их длина, пробки и время не входят в ограничения оптимизатора;
- физическая порча продукции отдельно не прогнозируется;
- вместо этого используется максимальное допустимое время доставки.
