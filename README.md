## Локальная демонстрация без внешнего интернета

Заранее установите зависимости: `python3 -m pip install -r backend/requirements.txt` и `npm ci` в `frontend`.
Из корня запустите `python3 -m uvicorn backend.main:app --host 127.0.0.1 --port 8000`, во втором терминале из `frontend` — `npm run dev -- --host 127.0.0.1`.
Откройте адрес Vite и выберите адрес по умолчанию «село Большие Кабаны, Республика Татарстан»: координаты и пять демонстрационных покупателей доступны локально. Расчёт выполняется настоящим локальным API.
Без интернета новый произвольный адрес не определяется: интерфейс предлагает явно выбрать демонстрационный адрес. При недоступности OpenStreetMap остаётся схема точек, пунктир обозначает условные линии, а не дороги. Выбор покупателей и расчёт продолжают работать. Публичный деплой этим сценарием не проверяется.

**«Спаси урожай: логистика на грани»** в направлении «Сельское хозяйство».

## 💡 О проекте

После сбора урожая времени мало: продукция портится, покупатели предлагают разные цены, транспорт ограничен, а стоимость доставки отличается.

**Спаси урожай** — это веб-сервис, который рассчитывает оптимальный план поставок скоропортящейся продукции с учетом:

- 🍓 запасов продукции;
- 🛒 спроса покупателей;
- 💰 закупочных цен;
- 🚚 доступности и грузоподъемности транспорта;
- ❄️ холодильного оборудования и прибавки к допустимому времени доставки;
- ⏱️ допустимого времени доставки;
- 🛣️ стоимости рейсов.

Пользователь меняет исходные условия и нажимает «Пересчитать». До успешного ответа прежние показатели помечаются устаревшими. Сравнение до/после относится к расчётам по всем найденным покупателям; альтернативы на третьем шаге — к одному расчёту по выбранным направлениям.

---

## 🎯 Цель оптимизации

Мы максимизируем прибыль:

```text
прибыль = выручка - транспортные затраты
```

При этом система не допускает:

- превышения запасов;
- превышения спроса покупателей;
- превышения грузоподъемности машин;
- использования недоступного транспорта;
- доставки скоропортящегося товара слишком медленным маршрутом.

---

## 🧠 Как работает алгоритм

Для оптимизации используется **MILP — смешанное целочисленное программирование** на базе PuLP.

Основная переменная:

```text
shipment[product, buyer, vehicle]
```

Она показывает, сколько конкретного товара отправить конкретному покупателю конкретной машиной.

Также используются бинарные переменные:

```text
vehicle_used[vehicle]
route_used[vehicle, buyer]
```

Они определяют:

- используется ли автомобиль;
- выполняется ли рейс к конкретному покупателю.

Алгоритм сам выбирает наиболее выгодную допустимую комбинацию поставок.

## 📦 Что учитывает модель

Для каждого продукта задаются:

- остаток на складе;
- максимальное допустимое время доставки.

Для каждого покупателя:

- положение в радиусе до 700 км от введённого адреса фермы;
- спрос;
- закупочная цена по каждому виду продукции.

Для транспорта:

- грузоподъемность;
- доступность;
- фиксированная стоимость использования;
- время доставки до каждого покупателя;
- стоимость рейса до каждого покупателя.
- прибавка к допустимому времени доставки для машин с холодильником.

### Допущения расчёта

Компании и спрос демонстрационные, точки выбираются из ограниченного локального каталога реальных городов. Для продолжения нужны 4–5 покупателей с расчётным расстоянием до 700 км; радиус автоматически не увеличивается.
Расстояние = расстояние по прямой × 1,18 с округлением до километра. Время = расстояние / 70 км/ч, минимум 0,5 ч и округление до 0,1 ч; поправка на машину по порядку каталога +0 / +0,15 / +0,30 / +0,45 ч. OSRM визуализирует дороги, но его длины и время не используются в ограничениях оптимизатора.
Вместимость ограничивается суммарно за расчётный цикл. Последовательность остановок и суммарное время многоадресного рейса не рассчитываются. +8/+12 часов холодильника — условная прибавка к допустимому времени доставки. Остатки — неотгруженный объём, не доказанная физическая порча; оценка риска основана только на запасе времени.
«До фикс. затрат» направления = выручка минус затраты направления. Фиксированная стоимость использованной машины вычитается один раз в итоговой прибыли плана; произвольного распределения этой стоимости между направлениями нет.

## 🔄 Сценарий для защиты

Мы специально реализовали сценарий из постановки кейса.

1. Загружается исходный набор данных.
2. Система рассчитывает оптимальный план.
3. Пользователь видит прибыль, расходы, остатки и поставки.
4. Одна машина переводится в состояние `unavailable`.
5. Одному покупателю повышается цена на клубнику.
6. Выполняется повторный расчет.
7. Система показывает новый план.
8. Можно сравнить результат **до / после** и убедиться, что все ограничения соблюдены.

Таким образом можно показать, что решение не захардкожено, а действительно пересчитывается оптимизатором.

## 🧩 Допущения

Проект создан как hackathon-MVP и использует демонстрационные данные.

В модели приняты следующие упрощения:

- один расчет рассматривается как один расчетный цикл;
- автомобиль имеет ограниченную общую грузоподъемность;
- одна машина может обслужить несколько покупателей;
- для каждой пары `машина → покупатель` задается условное время доставки;
- стоимость рейса учитывается один раз для каждой используемой пары `машина → покупатель`;
- дороги OSRM отображаются только на карте; их длина, пробки и время не входят в ограничения оптимизатора;
- физическая порча продукции отдельно не прогнозируется;
- вместо этого используется максимальное допустимое время доставки.
